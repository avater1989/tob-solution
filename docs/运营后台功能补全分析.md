# 运营后台功能补全分析

> 视角：平台运营方（艺博教育科技）
> 输入：结合【商家管理后台】（`prototype/admin/`，109 页）与【C 端小程序】（`prototype/miniprogram/`，8 页）现有能力
> 输出：运营后台（`prototype/ops/`，40 页）的功能缺口清单、建议功能与信息架构、优先级、待确认问题
> 版本：v0.1 ｜ 状态：待评审

---

## 一、三端职责边界（现状）

| 端 | 角色 | 核心职责 | 现有模块 |
|---|---|---|---|
| 商家管理后台 | 商户管理员/助教/销售/财务 | 租户内经营闭环 | 工作台、SCRM、直播、内容、小程序、交易、用户、经营分析、系统管理（9 个一级） |
| C 端小程序 | 家长/学员 | 消费与学习 | 首页、课程、直播列表、直播间、领课、我的、学习、支付结果（8 页） |
| 运营后台 | 平台运营/风控审核/财务结算 | 平台侧治理与监管 | 工作台、内容（含平台审核）、全局数据、系统管理（顶栏仅 4 个一级，租户/套餐/应用/角色被折叠进「系统管理」） |

**一句话**：商家端管「怎么把课卖出去」，C 端管「用户怎么买和学」，运营端目前只做了「开通租户 + 内容上架前审核 + 看全局数据」，**治理链和资金链尚未闭环**。

## 二、你提到的能力：现状对照

| 你提出的能力 | 运营后台现状 | 结论 |
|---|---|---|
| 商家的客户线索及资料 | 线索池（`leads.html`）在**商家后台**；运营后台只有租户列表、租户用户、租户部门/角色，无平台侧客户视图，也无商家资质资料 | ❌ 缺失，需新增 |
| 商家的小程序内容审核 | `ops/audit.html` 已覆盖 系列课/视频/图文/商品/直播 的**上架前**审核（直播走 `ProtoBiz` 的 `pending_platform_review`） | ⚠ 部分覆盖，缺店铺装修/商品/评价/UGC 及上架后巡检 |
| 商家直播内容审核 | 同上，仅审核**开播前**的标题/封面/挂载商品 | ⚠ 部分覆盖，缺**直播中**实时审核与处置 |
| 不合规内容强行下架 | 无。现有「驳回」只作用于未发布内容；PRD 5.3.1 的「强制下架」落在商家侧，平台侧无入口 | ❌ 缺失，需新增 |
| 运营后台发布内容被商家用户购买 → 运营后台接收订单 | 运营后台有「内容中台」（`content-*`），有「全局订单」（`orders.html`）但**只读**；缺平台自营订单接收、交付、权益开通 | ❌ 缺失，需新增 |
| 开通权益 | 商家后台有 `entitlement.html`（权益开通记录）；运营后台无权益管理 | ❌ 缺失，需新增 |
| 平台与商家对账 | 商家后台有 `recon`/`settlement`/`withdraw`/`bills`；运营后台仅在 `data.html` 内嵌一段**静态**「平台结算总览」 | ❌ 缺失，需独立模块 |

## 三、缺口分析与建议功能

### A. 商家与客户资料域

**现状**：`register.html`（商家入驻申请）文案承诺「信息将作为合作线索由商务顾问跟进」，但原型中**没有任何页面承接这批线索**——`ops/tenants.html` 只有状态为「待开通」的租户记录，没有招商线索的分配、跟进、转化过程。

**建议新增**

| 功能 | 说明 | 优先级 |
|---|---|---|
| 招商线索池（入驻申请） | 承接 `register.html` 留资：姓名/手机号/公司/角色/需求描述；支持分配商务、跟进记录、状态流转（待联系→跟进中→已开通/已拒绝）、去重 | P0 |
| 商家资质与证照管理 | 营业执照、法人身份、办学许可、EDI/网文/ICP 等资质上传、审核、到期预警（对应 PRD §9 资质风险） | P0 |
| 商家资料档案 | 一个商家一个档案：主体信息、资质、合同、联系人、服务费率、套餐、绑定应用、历史变更 | P0 |
| 客户资料合规查看 | 因多租户隔离，平台**默认不可见**商家 C 端客户明细；仅客服/纠纷/监管场景按单次授权查看，且解密留痕（复用商家侧 `user:list:decrypt` 的留痕思路） | P1 |
| 平台级客户线索洞察 | 不做明细穿透，只做聚合洞察：各租户线索量、转化率、活跃度（脱敏） | P2 |

> 关键约束：**客户资料是商户资产**，运营后台应以「聚合监管」为主、「个案授权查看」为辅，避免破坏多租户信任。

### B. 内容审核域

**现状**：`audit.html` 是最完整的 ops 页，覆盖 4 类内容 + 直播，支持通过/驳回/批量通过并写回 `ProtoBiz`。但审核范围与深度不足。

**建议新增**

| 功能 | 说明 | 优先级 |
|---|---|---|
| 审核范围补齐 | 增加：小程序店铺装修（`mp-home`/`mp-settings` 的首页模板、店铺信息）、商品与价格、优惠/活动话术、C 端评价与评论、测评/表单等 UGC | P0 |
| 上架后巡检 | 审核不只在上架前；对已发布内容做抽查/巡检（抽检比例、命中即进处置流程） | P1 |
| 举报与投诉受理 | C 端用户举报入口 → 平台工单 → 核实 → 处置 → 反馈；与商家客服工单区分 | P0 |
| 审核策略配置 | 敏感词库、行业违规词、AI 图文/视频审核开关、命中分级（提醒/驳回/下架）、审核 SLA 与超时升级 | P1 |
| 审核申诉与复核 | `audit-records.html` 已有「申诉」按钮但只是 toast；需落地申诉流程、复核队列、二次裁定 | P1 |

### C. 不合规内容处置域（强制下架）

**现状**：完全缺失。现有状态机里「平台侧」只有 `approved` / `platform_rejected` 两个动作，没有对**已上架**对象的处置能力。

**建议新增**

| 功能 | 说明 | 优先级 |
|---|---|---|
| 内容强制下架 | 对系列课/视频/图文/直播/商品一键下架，C 端即时不可见，同步通知商家（站内信/企微），记录处置人、原因、时间 | P0 |
| 直播实时处置 | 直播中：弹警告 / 断开推流 / 关闭直播间；配合评论审核（禁言、拉黑、撤回） | P0 |
| 账号与店铺处置 | 警告 → 限流 → 禁言 → 停用商家账号 → 封店；与 `tenants.html`「停用租户」打通（停用后商家后台只读、C 端全下架） | P0 |
| 违规处置工单 | 违规证据留存、处置动作、影响范围、商家申诉、平台复核、结案；形成可追溯台账 | P0 |
| 风控规则 | 退款率/投诉率/敏感命中率等阈值告警（`data.html` 已出现「退款率 7 日 21% 超阈值 15%」的示意，需要真实规则配置） | P1 |

### D. 平台自营内容 → 订单接收 → 权益开通

**现状**：运营后台能创建「平台标准内容」（`content-series` 等），但：
1. 没有「平台内容分发给哪些租户售卖」的授权管理；
2. 商家 C 端用户买了平台内容后，订单虽进「全局订单」但**只读**，没有平台侧交付与权益动作。

**建议新增**

| 功能 | 说明 | 优先级 |
|---|---|---|
| 内容授权与分发 | 平台内容按租户/套餐授权，控制「哪些商家可售卖、分成比例、上下架权」；商家侧被动感知 | P0 |
| 平台自营订单中心 | 接收平台内容订单：付款确认 → 交付 → 权益开通 → 退款/回收；与商家订单区分归属 | P0 |
| 权益管理 | 权益开通/回收/延期/赠送记录，支持按用户/订单/商品查询；与 `entitlement.html` 对齐口径 | P0 |
| 平台内容销售分成 | 平台内容销售额在平台与商家间的分成计算，产出结算依据 | P1 |

### E. 平台与商家对账结算域

**现状**：资金链路在商家后台已相对完整（资产、账单、提现、对账、结算、收款清分、分账规则、开票），但**平台侧只有一段静态总览**，无法真正完成「对账 → 结算 → 打款」。资金链路为：支付进入平台备付金 → T+1 对账无差异后按「服务费 + 商户」分账。

> ⚠ 原型中「平台服务费」存在 1%（`settlement`/`data`/`plans`）与 10%（`split-rules` 抽佣）两套口径，开发前须先统一。
>
> 📄 本域已补全为详细设计（字段、状态机、页面清单、数据模型、EARS 验收、待确认问题）：[`运营后台-交易与结算域-详细设计.md`](运营后台-交易与结算域-详细设计.md)。

**建议新增（独立「交易与结算」模块）**

| 功能 | 说明 | 优先级 |
|---|---|---|
| 结算规则配置 | 服务费率（按租户/套餐/合同覆盖）、账期 T+N、结算门槛、最低留存、是否需先开票 | P0 |
| 平台-商家对账单 | 按账期生成：交易明细、退款冲减、服务费、应结金额；支持商家确认/申诉；对应商家侧 `recon` badge 的差异数 | P0 |
| 差异处理工单 | 对账差异（短款/多款/退款时点）登记、举证、补差、挂账、结案 | P0 |
| 结算审核与打款 | 结算单复核 → 财务确认 → 打款 → 回执；状态可视 | P0 |
| 提现审核 | 商家提现申请 → 平台审核（额度、风控、留存）→ 打款 | P0 |
| 发票管理 | 平台向商家开票 / 商家开票给平台；开票状态与结算联动 | P1 |
| 平台服务费台账 | 服务费收入、退款冲减、开票、到账，产出平台侧收入报表 | P1 |
| 资金风控 | 备付金余额、账期占用、冻结/保证金、异常提现拦截 | P1 |

## 四、建议的信息架构（运营后台）

现有顶栏仅 4 个一级，把「租户/套餐/应用/角色」都塞进「系统管理」，随功能增多会失衡。建议重构为：

```
运营后台
├─ 1. 工作台           平台待办、全局核心指标、风险预警
├─ 2. 商家与租户       招商线索 · 商家列表 · 商家资料/资质 · 商家账号 · 套餐/应用授权
├─ 3. 内容与审核       内容中台 · 审核工作台 · 审核记录 · 举报投诉 · 违规处置（强制下架）· 审核策略
├─ 4. 交易与结算       全局订单 · 平台自营订单 · 权益管理 · 对账管理 · 结算管理 · 提现审核 · 发票 · 服务费台账
├─ 5. 全局数据         经营总览 · 租户排行 · 内容/交易/风控专题
└─ 6. 系统管理         运营账号 · 部门 · 角色权限 · 资源 · 字典 · 操作日志 · 公告协议
```

> 调整要点：把「内容审核」从内容模块独立成域；把「交易与结算」从全局数据里拆出来成为一等模块；把「商家资料/资质」并与租户管理形成「商家与租户」域。

## 五、优先级建议

| 优先级 | 功能集合 | 理由 |
|---|---|---|
| **P0** | 招商线索池、商家资质资料、审核范围补齐、举报投诉、强制下架、直播实时处置、账号店铺处置、平台自营订单+权益开通、结算规则、对账单、差异工单、结算审核、提现审核 | 平台治理底线 + 资金闭环，缺失则无法对商家履约 |
| **P1** | 上架后巡检、审核策略配置、申诉复核、风控阈值、内容授权分成、发票、服务费台账、资金风控、公告协议、全局审计日志、客服纠纷 | 提升治理效率与合规性 |
| **P2** | 商家考核评分、平台运营活动、三方依赖监控、模板字典、客户聚合洞察 | 运营精细化，可后置 |

## 六、待确认问题清单

1. **客户资料边界**：平台侧是否需要查看商家 C 端客户明细？若需要，授权规则、留痕与合规口径是什么？（建议默认聚合、个案授权）
2. **平台自营内容的商业模式**：是「平台供货给商家卖」还是「平台自己卖」？前者只需授权+分成，后者需要完整订单/交付/售后。
3. **权益归属**：权益由平台统一发放，还是各商家独立发放？跨商家权益是否通用？
4. **结算主体**：资金是否统一走平台备付金？商家是否有自有商户号（PRD 提到为后续能力）？这决定对账是「平台分账」还是「平台代收」。
5. **审核责任边界**：直播实时内容由平台审核还是商家自审+平台兜底？直接关系资质与封禁风险。
6. **强制下架权限**：谁有权下架/封店？是否需要双人复核？处置与商家申诉的 SLA？
7. **商家资质清单**：不同类目（家庭教育/心理/学科）需要哪些资质？到期未续如何处理？
8. **多租户数据隔离强度**：平台运营的「数据范围」权限（`sys-roles.html` 已有「全部/指定租户/本人」）如何落到每个新功能？
