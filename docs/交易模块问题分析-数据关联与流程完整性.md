# 交易模块问题分析：数据关联性 × 流程完整性

> 版本：v0.1 ｜ 日期：2026-09-11 ｜ 状态：待评审
> 分析对象：商家后台「交易」18 页 + 运营后台「交易与结算」10 页
> 基准依据：`WBDY/艺博教育通联云商通对接方案.docx`、`docs/ToB-PRD-待决策与P0冻结表.md`、`prototype/` 现状
> 方法：以通联云商通方案的**参与主体 / 资金路径 / 前置资质 / 对账口径**为基准，逐项与原型比对

---

## 一、结论速览

**核心判断**：当前原型的交易模块是「**电商式收单 + 分账**」骨架（平台商户收单 → 按比例分账 → 商家提现），而通联云商通方案是「**银行弱存管 + 托管代收/代付 + 会员进件 + 提现签约**」的托管模式。两者在参与主体、资金路径、前置资质、对账方式上都不一致——所以问题不是「补几个页面」，而是**缺一条主链**。

**你提的三点，定性如下**：

| # | 你的判断 | 定性 | 严重度 |
|---|---|---|---|
| 1 | 缺少进件模块 | ✅ 成立。全站「进件」只作为名词出现在 6 个页面，**没有任何进件流程页**；「签约」「存管」「收款主体」「账户集」「头寸」在全站 **0 次出现** | 阻塞收款 |
| 2 | 分账要按内容来源走两套逻辑 | ✅ 成立且更严重。当前数据模型**无法区分**订单归属，且分账比例口径有 **6 个不同数字**在流转 | 阻塞对账 |
| 3 | 商家资产模块重复、交易设置不该由商家配 | ✅ 成立。商家侧 5 个资产页与运营侧 3 个结算页职责重叠；「交易设置」4 个页全部是平台级配置却放在商家侧 | 架构错位 |

**额外发现的高优问题**：退款受「账户余额约束」但原型无此概念；提现缺签约校验；对账缺「订单状态查询」兜底；且 `aftersales.html` / `aftersale-detail.html` 仍残留换货/发货/库存/物流的实物电商语义。

## 二、基准：通联云商通方案要求什么

来源：《艺博教育通联云商通对接方案》。要点与原型现状比对：

| 方案要求 | 对系统的能力要求 | 原型现状 |
|---|---|---|
| 艺博为大 B 签约云商通，**银行弱存管**（通联+艺博+招商银行三方协议） | 存管主体、三方协议备案 | ❌ 全站无「存管」概念 |
| 收款后可 **D+1 结算到银行存管模式** | 结算时点与存管账户联动 | ⚠ 仅有「T+1 自动分账」 |
| **入金收款商户**：艺博旗下子公司为收款主体（名称无「教育」），**按省份开通多个商户号**，资金统一结算到艺博存管账户 | 收款主体管理、多商户号管理、资金归集 | ❌ 全站无「收款主体」，`payment.html` 只有一个 `TL-MCH-8801XXXX` |
| 支付方式：APP 调用微信/支付宝 → **通联小程序收银台** | 收银台唤起、渠道配置 | ⚠ `payment.html` 有「通联支付 / 微信直连备用」，但无收银台与渠道参数 |
| 角色 4 类：平台方大 B、加盟代理商小 B、付款小 C、（收款方） | 多主体建模 | ⚠ 只有「平台 / 商户」两层 |
| **会员类**：创建会员（企业 memberType=2 / 个人 =3）、设置企业信息（工商+法人实名）、影印件采集（营业执照必传、法人身份证正反必传、开户证明可选，OCR 校验，单张≤1M）、获取会员信息（一致性字段）、短信验证码（绑定 9/解绑 6）、绑定手机（**绑定后才能创建订单**） | 商家进件流程 + 资料管理 + 审核状态 | ❌ 无进件页，`payment.html` 只有一行「进件状态：已通过」 |
| **账户提现协议签约**：H5 三方协议（会员/平台/通联），返回 `ContractNo` 需保存；个人须先实名、企业须先企业信息审核通过；**未签约会员将控制提现功能** | 签约流程 + 签约状态 + 提现前置校验 | ❌ 全站「签约」0 次出现 |
| **订单类**：托管代收 →（平台中间**账户集 10004** 记账）→ 单笔/批量**托管代付**，**支持多级分账，规则在 `splitRule` 字段传输** | 托管代收/代付单据、账户集、分账规则下发 | ⚠ 只有「分账」概念，无托管单据、无账户集 |
| **提现**：`payMethod=WITHDRAW_TLT`；`withdrawType` = D0 单笔实时代付 / D0customized 每整点 / D1（D+1 日 14:00）/ T1customized（T+1 工作日） | 提现模式配置与状态机 | ❌ 无 withdrawType，`withdraw.html` 只有「自动/手动」 |
| **退款**：当日退货金额 < 当日交易金额；且 < 原订单**收款人账户余额**（不足需先充值） | 退款余额校验 + 充值/垫资流程 | ❌ 无此约束，`refunds.html` 无余额概念 |
| **对账**：订单状态查询（异步通知不保证 100% 到达，强烈建议对接）；**平台头寸查询**（通联通头寸 / 电子账户头寸） | 主动查询兜底 + 头寸视图 | ⚠ `recon.html` 有 T+1 账单核对，无主动查单、无头寸 |
| 费用：入金 **0.3%**（或 0.28%）、系统费（免费需年流水 5000 万，或首年 3 万/次年 2 万）、提现 **1 元/笔**、认证 **5 元/次** | 计费口径 | ❌ `payment.html` 写「0.6%（按协议，可议价）」，与方案 0.3%/0.28% 不一致 |

## 三、问题清单

### A. 数据关联性（实体、字段、口径对不上）

| 编号 | 问题 | 证据 | 影响 |
|---|---|---|---|
| **A1** | **参与主体模型缺失**：只有「平台 / 商户」两层，缺「加盟代理商（小B企业会员）」「收款个人」「艺博入金收款主体」三类主体 | 全站无会员号体系（`MEM-1001XX` 是硬编码文案）；无 `bizUserId`/`userId` 映射 | 进件、分账、提现、对账全部无法落表 |
| **A2** | **「商户号」一词三义**：① 艺博入金收款主体商户号（按省多个）② 平台商户号 ③ 商家自有商户号（待决策 D2 链路二） | `payment.html` 只有 `TL-MCH-8801XXXX` 一个平台商户号；`待决策 D2` 提到「绑定商户号（链路二入口）」但无页面 | 收款路径、费率、开票主体全部无法区分 |
| **A3** | **分账/费率口径 6 个数字并存** | `settlement.html` 商户 99% / 平台 1%；`split-rules.html` 平台抽佣 10% / 12% / 15% / 5%；`bills.html` 「通联支付费率 1%」；`payment.html` 「0.6%」；`ops/plans.html` 服务费率 1% / 0.6%；`待决策 F4` 「对标小鹅通约 2%」；通联方案入金 0.3%/0.28% | **平台账与商家账必然对不上**，开发无法开工 |
| **A4** | **订单缺少「资金归属」字段**：无法判断一笔订单是「平台内容」还是「商家自建内容」，也就无法决定分账走哪条链路 | `orders.html` / `order-detail.html` 无 `content_source`、`settle_mode` 字段 | 你的第 2 点无法实现 |
| **A5** | **收款账户体系缺失**：无「商家结算卡 / 提现签约状态 / 收款主体 / 入金商户号」实体 | `withdraw.html` 里结算卡是写死文案；`payment.html` 分账会员表有「绑定结算卡」但无维护入口 | 提现无法校验，签约状态无处存 |
| **A6** | **退款缺少余额约束字段**：方案的「当日退货额 ≤ 当日交易额、且 ≤ 原收款人账户余额」没有落点 | `refunds.html` / `aftersales.html` 无余额、无充值概念 | 退款会失败且无处置路径 |
| **A7** | **提现缺少 `withdrawType`（4 种时点）** | `withdraw.html` 只有「自动提现（每日 08:00）/ 手动」 | 与通联代付时点对不上 |
| **A8** | **缺少账户集 / 头寸维度** | 「账户集」「头寸」全站 0 次 | 平台侧无法看资金池真实状态 |
| **A9** | **套餐服务费率未落到订单** | `ops/plans.html` 有服务费率，但订单/结算单未冗余 `service_fee_rate` | 费率改版后历史订单会被追溯重算 |
| **A10** | **权益与内容来源未关联** | `entitlement.html` 只记「权益开通/回收」，未区分平台内容权益 / 自建内容权益 | 平台内容的权益回收责任方不清（谁退、谁回收） |

### B. 流程完整性（链路断了）

| 编号 | 问题 | 现状 | 缺口 |
|---|---|---|---|
| **B1** | **进件链路完全缺失**（阻塞收款） | 仅 `payment.html` 一行「进件状态：已通过」 | 缺：提交资料 → 影印件上传/OCR → 企业信息核验 → 通联审核 → 审核结果回写 → 绑定手机 → 提现签约 → 可收款 |

## 四、你提的三点：建议方案

### 4.1 进件模块（建议新增）

**归属**：分两端放——商家侧「提交资料」，运营侧「审核与主体管理」。

| 页面 | 端 | 说明 | 优先级 |
|---|---|---|---|
| 进件申请 / 开通收款 | 商家后台 | 主体类型（企业/个人）、营业执照、法人身份证正反面、开户证明（可选）、联系人、结算卡；上传即 OCR 预检 | P0 |
| 进件进度 | 商家后台 | 状态机可视化 + 驳回原因 + 重新提交 | P0 |
| 提现协议签约 | 商家后台 | H5 三方协议唤起、`ContractNo` 回显、签约状态 | P0 |
| 进件审核工作台 | 运营后台 | 待审列表、资料查看、通过/驳回、同步通联审核结果 | P0 |
| 收款主体与商户号 | 运营后台 | 艺博入金收款主体、按省份商户号、资金归集到存管账户 | P0 |
| 会员管理 | 运营后台 | 会员号（`bizUserId` ↔ userId）、类型、绑定手机、签约状态 | P1 |

**状态机建议**：`未提交 → 资料待补 → 平台初审中 → 通联审核中 → 审核通过（待签约） → 已签约（可收款）`；驳回分支：`已驳回 → 资料待补`。

**EARS**
- Ubiquitous：系统应始终保证「未完成绑定手机」的商家不能创建订单。
- State-driven：当商家签约状态为「未签约」时，系统应禁止其发起提现并引导签约。
- Unwanted：若通联审核驳回，则系统应记录驳回原因并允许商家修改资料后重新提交。
- Event-driven：当收到通联审核结果异步通知时，系统应更新进件状态并通知商家。

### 4.2 分账双链路（你的第 2 点）

**链路 A · 平台内容**（运营后台下发的内容）
```
用户支付 ¥100 → 艺博入金收款主体 → 艺博存管账户
  ├─ 商家（小B）：拿「佣金」= ¥100 × 佣金率
  └─ 艺博平台：留存剩余（¥100 − 佣金）
splitRule = [{ 商家, 佣金率 }, { 艺博, 1 − 佣金率 }]
```
**链路 B · 商家自建内容**
```
用户支付 ¥100 → 艺博入金收款主体 → 艺博存管账户
  ├─ 商家（小B）：拿「课程金额 − 平台服务费」= ¥100 − (¥100 × 服务费率)
  └─ 艺博平台：收「服务费」= ¥100 × 服务费率（按套餐/合同）
splitRule = [{ 商家, 1 − 服务费率 }, { 艺博, 服务费率 }]
```

**对数据模型的要求**（建议订单/结算单冗余快照，避免历史订单被新规则追溯）：

| 字段 | 取值 | 说明 |
|---|---|---|
| `content_source` | `platform` / `self` | 内容来源，决定走哪条链路 |
| `settle_mode` | `commission` / `service_fee` | 佣金模式 / 服务费模式 |
| `commission_rate` | 百分比 | 链路 A 用 |
| `service_fee_rate` | 百分比 | 链路 B 用，来源：套餐 / 租户合同 |
| `payee_member_id` | 会员号 | 收款方（商家小B会员） |
| `platform_merchant_id` | 商户号 | 艺博入金主体 |
| `split_rule_snapshot` | JSON | 下单时的分账规则快照 |

**连带影响**：
- **退款**：链路 A 退的是艺博账户的钱；链路 B 退的是商家账户的钱（受余额约束）。两条链路的退款可用余额校验对象不同。
- **发票**：链路 A → 商家给艺博开票（佣金）；链路 B → 艺博给商家开票（服务费）。
- **权益**：平台内容的权益回收由平台主导，商家侧不可删。

**EARS**
- Ubiquitous：系统应始终按订单的 `content_source` 选择唯一的分账链路，同一订单不得同时命中两条链路。
- State-driven：当订单为平台内容时，系统应按 `commission_rate` 给商家分账佣金，剩余留存平台账户。
- State-driven：当订单为商家自建内容时，系统应按 `service_fee_rate` 扣收平台服务费，剩余分账给商家。
- Event-driven：当订单生成时，系统应固化 `split_rule_snapshot`，后续规则变更不影响该订单。

### 4.3 资产重复与交易设置上移（你的第 3 点）

**目标职责划分**：

| 能力 | 商家后台 | 运营后台 | 通联 |
|---|---|---|---|
| 进件资料提交 / 进度 → 我建议→ (商家) | ✅ | 审核 | 审核 |
| 收款主体 / 商户号 / 收单渠道 | 只读 | ✅ 配置 | — |
| 分账规则 / 结算规则 | 只读 | ✅ **唯一配置入口** | 执行 |
| 对账（对账单） | 只读结果 + 确认/申诉 | ✅ 生成、复核 | 数据源 |
| 结算单 | 确认 + 查看打款回执 | ✅ 复核、打款 | 代付 |
| 提现 | 申请 + 签约 | ✅ 审核 | 代付 |
| 订单 / 权益 / 退款 / 售后 | ✅ 主营 | 只读 | — |
| 资产总览 / 交易账单 | ✅ 保留（**只读结果视图**） | — | — |
| 开票 | 查看 / 接收 | ✅ 双向开具 | — |
| 服务费台账 / 资金风控 | 不可见 | ✅ | — |

**具体动作**：
1. **商家后台「交易设置」整组下架**（收款与清分 / 分账规则配置 / 开票设置 / 交易选项 4 页），能力迁至运营后台；商家侧最多保留只读的「费率与账期查询」。
2. **商家资产模块收敛**：保留「资产总览 + 交易账单」（只读余额与流水），把「对账管理 / 结算单 / 提现管理」定位为「平台结果视图 + 商家确认动作」，与运营后台的生成/审核/打款形成主从关系，避免两边都能发起。
3. **统一入口**：对账、结算、提现的**发起方在平台**，商家只做「确认 / 申诉 / 申请提现」。

## 五、优先级建议

| 优先级 | 事项 | 理由 |
|---|---|---|
| **P0（阻塞收款与对账）** | A1 主体模型、A3 费率口径统一、A4 订单资金归属、B1 进件链路、B3 分账双链路、B7/B8 职责重划分 | 不解决则无法真实收款、无法对账 |

## 六、待确认问题

1. **费率口径**：1% / 2% / 10% / 0.6% / 0.3% 到底哪个是交易抽佣、哪个是 SaaS 订阅费？链路 A 的佣金率与链路 B 的服务费率分别定多少？
2. **服务费性质**：「服务费率」是交易抽佣，还是 SaaS 年费（¥4,980/9,800/19,800）？两者是否叠加？
3. **收款主体**：艺博用哪几家子公司、开几个省的商户号？资金归集到哪个存管账户？
4. **链路 B 的资金性质**：商家自建内容的钱先过艺博存管账户，是「代收代付」还是「平台自营转售」？直接影响开票与税务。
5. **进件范围**：本期是否真的做进件（受 E4 合同状态制约）？若不做，试点商家如何收款？
6. **退款余额不足**：由商家充值、平台垫资，还是直接不允许退款？
7. **提现时点**：四种 `withdrawType` 选哪种？是否按商家配置？
8. **平台内容权益**：平台内容售出后，退款与权益回收由平台还是商家执行？
9. **商家侧资产范围**：`待决策 D6` 建议一期只做「订单+权益+退款」，那商家侧资产总览/账单是否也一并推迟？
