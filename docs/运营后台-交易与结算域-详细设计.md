# 运营后台 · 交易与结算域详细设计

> 版本：v0.1 ｜ 状态：待评审 ｜ 范围：【运营后台】平台侧「交易与结算」域
> 依赖：通联支付（通商云）平台商户 + 会员进件分账、商家后台资产管理模块（`admin/assets · bills · withdraw · recon · settlement · payment · split-rules · invoice`）、`ops/orders.html`、`ops/data.html`
> 上游文档：`docs/运营后台功能补全分析.md` §三 E

---

## 1. 目标与边界

### 1.1 目标

在平台侧打通 **对账 → 结算 → 打款** 的资金闭环，使平台能够：
1. 配置并下发结算规则（费率、账期、门槛、留存）；
2. 自动生成平台-商家对账单，并让商家在线确认/申诉；
3. 处理对账差异，形成可追溯的差异工单；
4. 复核并执行结算打款、审核商家提现；
5. 沉淀平台服务费台账与资金风险预警。

### 1.2 端侧边界（谁做什么）

| 动作 | 商家后台（租户） | 运营后台（平台） | 支付渠道（通联/视频号小店） |
|---|---|---|---|
| 交易发生、订单与账单查看 | ✅ 主营 | 只读全局 | 收单 |
| 渠道账单拉取与逐笔核对 | 查看结果 | ✅ 执行 + 结果 | 提供账单 |
| 结算规则（费率/账期/门槛） | 只读 | ✅ 配置、下发、变更 | 按规则执行分账 |
| 对账单生成 | 查看/确认/申诉 | ✅ 生成、下发、复核 | 数据源 |
| 差异处理 | 举证、补充材料 | ✅ 登记、判断、处置 | 重取账单/回盘 |
| 结算单复核与打款 | 确认、查看回执 | ✅ 财务复核 + 打款 | 分账/代付 |
| 提现 | 申请、设置自动提现 | ✅ 审核、打款 | 代付 |
| 发票 | 申请开票 / 接收 | ✅ 双向开具与管理 | — |
| 服务费台账、资金风控 | 不可见 | ✅ 独占 | — |

### 1.3 MVP 不做

- 商户自有商户号直连（PRD 已标注为后续能力）；
- 多级分账的复杂规则引擎（嵌套分账、阶梯费率、按量计费）；
- 银行级资金存管改造、备付金账户自动对账；
- 跨账期自动补差、自动开票（P1 仅做人工触发）。

## 2. 资金与账务口径（统一基准）

### 2.1 资金链路

```
买家支付（微信小程序 / 直播间 / 视频号小店）
  → 通联支付平台商户号收单（全额收单）
  → 平台备付金账户
  → T+1 02:00 拉取渠道账单，与平台订单逐笔对账
  → 命中分账规则，分账至各分账方（通联会员：商户 / 平台 / 老师 / 推广人）
  → 商户可提现余额形成
  → 商户自动或手动提现 → 打款至结算卡
```

### 2.2 关键概念定义

| 概念 | 定义 |
|---|---|
| 交易额（GMV） | 账期内「支付成功」订单金额合计，按支付时间归属账期 |
| 退款额 | 账期内退款成功的金额，冲减当期应结算 |
| 渠道手续费 | 通联/微信收取的收单手续费，按支付渠道费率计 |
| 平台服务费（抽佣） | 平台按规则从交易额中抽取的收入 |
| 其他分账方分成 | 授课老师、推广人等按分账规则取得的份额 |
| 应结算金额 | 应付给商户的金额（见 2.3 公式） |
| 分账在途 | 已生成分账指令、渠道尚未回盘成功的金额 |
| 可提现余额 | 已分账到商户且未被冻结、未在提现中的金额 |
| 冻结金额 | 风控/纠纷/保证金占用的金额，不可提现 |
| 留存金额 | 商户设置的保留底额，自动提现时扣除 |
| 账期 | 结算周期口径（T+1 / T+7 / 周结 / 月结） |

### 2.3 计算公式

```
应结算 = 交易额 − 退款额 − 平台服务费 − 其他分账方分成 − 商户承担的渠道手续费
可提现余额 = 已分账到商户 − 已提现成功 − 提现中 − 冻结金额
```

### 2.4 口径统一（P0 前置，必须先定）

原型中「平台服务费」存在两套口径，**开发前必须二选一并全局对齐**：

| 位置 | 现值 | 含义推测 |
|---|---|---|
| `admin/settlement.html` 分账明细 | 商户 99% / 艺博 1% | 平台按交易额抽 1% |
| `admin/data.html` 平台结算总览 | 平台服务费(1%) | 同上 |
| `admin/plans.html` 套餐范围 | 服务费率 1% / 1% / 1% 或 0.6% | 同上 |
| `admin/split-rules.html` 分账规则 | 艺博平台抽佣 10% / 15% / 5% | 按商品/分组配置的分账抽佣 |

**建议**：以 `split-rules.html` 的「按商品/分组配置的分账抽佣比例」为**交易侧唯一抽佣口径**（支持按合同差异化，默认 10%），把 1% 澄清为「SaaS 订阅服务费」或直接废弃。统一后需回改 `settlement.html`、`data.html`、`plans.html` 的文案，避免平台与商家账不一致。

## 4. 功能详设

### 4.1 结算规则配置（P0）

**目标**：平台统一维护费率与账期规则，按租户/套餐/合同差异化覆盖，规则变更可追溯。

**配置项**

| 字段 | 类型 | 说明 |
|---|---|---|
| 规则名称 | 文本 | 必填 |
| 优先级 | 枚举 | 商品 > 商品分组/类目 > 租户/套餐/合同 > 全局默认 |
| 适用范围 | 枚举 | 全部商品 / 商品分组 / 商品类型 / 指定商品 / 指定租户 |
| 分账方与比例 | 明细 | 各方比例合计须 = 100%（含平台抽佣） |
| 抽佣方式 | 枚举 | 从分账金额扣除 / 先分账后单独结算 |
| 账期 | 枚举 | T+1 / T+7 / 周结 / 月结 |
| 结算门槛 | 金额 | 不足门槛顺延下期 |
| 最低留存 | 金额 | 账上保底，不参与结算/提现 |
| 是否需先开票 | 布尔 | 开启后需先收票再打款 |
| 生效时点 | 时间 | 仅对生效时间之后支付的订单生效 |
| 状态 | 枚举 | 草稿 / 生效中 / 已停用 |

**状态机**：`草稿 → 生效中 → 已停用`（可重新启用）；变更生成新版本，历史订单按原规则执行。

**页面**：`ops/settle-rules.html`（列表 + 新建/编辑弹窗 + 试算 + 规则说明），交互对齐 `admin/split-rules.html`。

**EARS 需求**
- Ubiquitous：系统应始终保证同一订单仅命中一条规则，命中优先级为 商品 > 分组/类目 > 租户/套餐/合同 > 全局默认。
- Event-driven：当规则的分账比例合计不等于 100% 时，系统应阻止保存并提示差额。
- State-driven：规则处于「生效中」时，系统应仅对生效时间之后支付的订单应用该规则。
- Unwanted：若某分账方未完成通联会员进件，则系统应阻止该方参与分账并在规则配置页给出明确提示。

### 4.2 平台-商家对账单（P0）

**目标**：按账期自动生成对账单，商家在线确认或申诉，作为结算依据。

**生成逻辑**：每日 02:00 拉取渠道账单，按「租户 × 账期 × 渠道」生成；对账通过后进入待结算池。

**对账单字段**

| 字段 | 说明 |
|---|---|
| 对账单号 | 如 `PRC20260407001`（平台侧，与商家侧 `RC…` 区分） |
| 租户 / 账期 / 渠道 | 通联支付 / 视频号小店 |
| 平台订单数 / 渠道账单笔数 | 用于笔数核对 |
| 交易额 / 退款额 / 服务费 / 应结金额 | 金额核对 |
| 差异笔数 / 差异金额 | 展示差异汇总 |
| 状态 | 待对账 / 已对平 / 有差异 / 待商家确认 / 已确认 / 商家已申诉 |
| 生成时间 / 商家确认人 / 确认时间 | 留痕 |

**明细维度**（对账单详情）：订单号、渠道交易单号、买家、商品、支付金额、退款金额、服务费、分账方与比例、对账结果（一致/差异类型）、账期归属。

**状态机**

```
待对账 ──对账完成──▶ 已对平 ──▶ 待商家确认 ──商家确认──▶ 已确认（可结算）
                        │                        └──商家申诉──▶ 商家已申诉 ──▶ 平台复核 ──▶ 已确认/重算
                        └──存在差异──▶ 有差异 ──差异处理完──▶ 重算 ──▶ 待商家确认
```

**页面**：`ops/recon.html`（对账单列表 + 筛选 + 汇总卡）、`ops/recon-detail.html`（明细 + 确认/申诉记录）。
**商家侧联动**：商家 `recon.html` 的「未平差异」badge 数与平台侧差异工单数同源，需统一数据口径。

**EARS 需求**
- Event-driven：当 T+1 对账完成且不存在未处理差异时，系统应将该对账单状态置为「待商家确认」并通知商家。
- Ubiquitous：系统应始终以「平台订单」与「渠道账单」按渠道交易单号逐笔匹配，不得仅比对汇总金额。
- Unwanted：若商家对账单发起申诉，则系统应暂停该账期的结算，直至申诉复核完成。
- State-driven：当对账单处于「有差异」状态时，系统应禁止其进入结算流程。

### 4.3 差异处理工单（P0）

**目标**：把对账差异变成有责任人、有 SLA、有结论的工单，避免差异长期挂账。

**差异类型**（对齐现有 3 类并扩展）

| 类型 | 说明 | 默认处置 |
|---|---|---|
| 金额不一致 | 平台与渠道金额不符（券后、优惠分摊等） | 重取账单 / 人工确认 |
| 平台单边账 | 平台有、渠道无（支付未成功却记成功） | 排查支付回调 → 修正订单 |
| 渠道单边账 | 渠道有、平台无（掉单） | 补单修复 |
| 退款状态不一致 | 退款时点/状态不同步 | 自动平账 / 人工确认 |
| 重复支付 | 同单多次支付 | 原路退多收款 |
| 跨期差异 | 归属账期错误 | 调账至正确账期 |

**工单字段**：工单号、来源对账单、差异类型、租户、平台记录、渠道记录、差值、发现时间、责任人、SLA、处理动作、处理说明、附件（举证）、状态、结案时间。

**状态机**：`待处理 → 处理中 → 已平账 / 已补差 / 已挂账 / 已关闭`；超 SLA 自动升级。

**处置动作**：重取渠道账单、人工确认、补单修复、补差调账、挂起（下期跟踪）、转客服/纠纷。

**页面**：`ops/recon.html` 的「差异处理」Tab + `ops/recon-diff-detail.html`（工单详情与时间轴）。

**EARS 需求**
- Event-driven：当差异工单被创建时，系统应按差异类型自动指派责任角色并设置 SLA 倒计时。
- Unwanted：若差异工单超过 SLA 未处理，则系统应升级提醒并标记为高优先级。
- Ubiquitous：系统应始终保留差异从发现到结案的全部操作记录与举证附件。

---

### 4.4 结算审核与打款（P0）

**目标**：结算单经商家确认、平台财务复核后打款，全程状态可视、凭证可查。

**结算单生成条件**：对账单已对平 + 无未结差异 + 已达结算门槛 + 商家已确认。

**字段**：结算单号、租户、账期、关联对账单、订单数、交易额、退款额、服务费、其他分账方分成、应结算金额、收款账户、状态、生成/确认/复核/打款时间、打款凭证、打款失败原因。

**状态机**

```
待生成 → 待商家确认 → 已确认 → 待财务复核 → 复核通过 → 打款中 → 已打款 → 已完结
                                    │                                      └──打款失败──▶ 打款异常（可重试）
                                    └──复核驳回──▶ 已退回（附原因）
商家申诉 / 资金冻结 ──▶ 结算暂停
```

**规则与边界**
- 打款为敏感操作，需**双人复核**（提交人 ≠ 复核人）与操作留痕；
- 支持批量打款与单笔重试；打款回执与电子回单可下载；
- 若开启「先票后款」，则未收票不得打款；
- 退款在后续账期冲减，不回滚已打款结算单。

**页面**：`ops/settlements.html`（结算单列表 + 筛选 + 统计）、`ops/settlement-detail.html`（金额构成 + 分账明细 + 打款信息 + 复核动作）。

**EARS 需求**
- State-driven：当结算单处于「待财务复核」时，系统应仅允许具备复核权限的角色执行通过/驳回。
- Event-driven：当打款指令提交成功后，系统应将结算单状态置为「打款中」并在收到渠道回执后更新为「已打款」。
- Unwanted：若打款失败（卡号异常/额度不足），则系统应保留原结算单并生成「打款异常」记录，支持原单重试而非新建。
- Optional：若规则开启「先开票后打款」，则系统应在未关联有效发票时阻止打款。

### 4.5 提现审核（P0）

**目标**：平台对商家提现申请做额度、风控、留存与账户一致性审核后打款。

**提现来源**：自动提现（按商户设置时间执行）、手动提现（商家发起）。

**审核规则**
1. 提现金额 ≤ 可提现余额（已扣除冻结与留存）；
2. 结算卡为已完成进件的同名对公/同主体账户；
3. 无未结差异、无进行中纠纷、无风控拦截；
4. 单笔/单日额度限制，超限转人工；
5. 高风险租户（退款率超标、被处置中）强制人工审核。

**状态机**：`待审核 → 审核通过 → 打款中 → 已到账`；`待审核 → 已驳回（附原因）`；`打款中 → 打款失败（可重试）`；自动提现可被风控规则直接拦截为「待人工审核」。

**页面**：`ops/payouts.html`（提现记录 + 审核动作 + 风控标记）、详情抽屉（申请信息 / 余额构成 / 审核记录 / 打款凭证）。

**EARS 需求**
- Event-driven：当商家发起提现申请时，系统应自动校验可提现余额、冻结金额与留存金额，校验不通过则直接驳回并给出原因。
- Unwanted：若租户处于风控拦截名单或存在未结差异，则系统应强制转人工审核而非自动通过。
- State-driven：当提现单处于「打款中」时，系统应冻结对应金额，避免重复提现。
- Ubiquitous：系统应始终校验提现结算卡与进件主体一致，不一致时禁止打款。

### 4.6 发票管理（P1）

**目标**：管理平台与商家之间的双向开票，并与结算联动。

**两个方向**

| 方向 | 场景 | 说明 |
|---|---|---|
| 平台 → 商家 | 平台服务费/抽佣开票 | 平台向商家开具技术服务费发票 |
| 商家 → 平台 | 商家开票给平台 | 用于平台成本入账（视结算主体而定） |

**字段**：发票申请号、租户、发票类型（增值税专票/普票）、开票主体、税号、开票金额、关联账期/结算单、状态、快递信息、申请人/时间。

**状态机**：`待开票 → 开票中 → 已开票 → 已寄出 → 已签收`；`已开票 → 已作废 / 已红冲`。

**与结算联动**：规则开启「先票后款」时，打款需关联有效发票；红冲需回退结算状态。

**页面**：`ops/invoices.html`。

**EARS 需求**
- Event-driven：当结算规则要求先开票时，系统应在结算单未关联有效发票的情况下阻止打款。
- Unwanted：若发票发生红冲或作废，则系统应标记关联结算单并提示人工复核。

---

### 4.7 平台服务费台账（P1）

**目标**：沉淀平台侧收入口径，产出可分租户/账期/商品/渠道的服务费报表。

**收入构成**：分账抽佣收入（主）+ SaaS 订阅服务费（如保留）+ 渠道手续费差（如有）。

**字段**：账期、租户、商品/分组、渠道、交易额、抽佣比例、服务费金额、退款冲减、开票状态、到账状态。

**报表维度**：按账期趋势、按租户排行、按商品/分组贡献、按渠道结构；支持导出。

**关系**：与 4.2 对账单、4.4 结算单、4.6 发票同源，形成「对账—结算—开票—收入」一致链路。

**页面**：`ops/fee-ledger.html`。

---

### 4.8 资金风控（P1）

**目标**：对资金与经营异常做监控、预警与自动拦截。

**监控项**

| 监控项 | 阈值示意 | 动作 |
|---|---|---|
| 备付金余额 | 低于安全水位 | 告警 |
| 账期占用 | 超期未结算金额 | 告警 + 列待办 |
| 冻结/保证金 | 变更需留痕 | 人工复核 |
| 异常提现 | 频率/额度异常 | 自动拦截转人工 |
| 退款率 | 7 日 > 15% | 告警 + 限制提现 |
| 分账失败 | 结算卡异常 | 告警 + 重试 |
| 对账差异 | 未结差异笔数/金额 | 告警 |

**动作**：阈值告警（进 `ops/dashboard.html` 平台待办）、自动拦截提现、自动暂停结算、人工复核队列。

**页面**：`ops/fund-risk.html`；预警统一汇入运营工作台「平台待办」。

**EARS 需求**
- Event-driven：当租户 7 日退款率超过阈值时，系统应自动限制该租户提现并生成风控待办。
- Unwanted：若分账连续失败超过 N 次，则系统应暂停该租户后续分账并通知运营介入。
- State-driven：当租户处于「风控限制」状态时，系统应仅允许人工审核通过其提现与结算。

## 7. 状态机汇总

| 对象 | 状态流转 |
|---|---|
| 结算规则 | 草稿 → 生效中 → 已停用（可重新启用） |
| 对账单 | 待对账 → 已对平 / 有差异 → 待商家确认 → 已确认 / 商家已申诉 |
| 差异工单 | 待处理 → 处理中 → 已平账 / 已补差 / 已挂账 / 已关闭 |
| 结算单 | 待生成 → 待商家确认 → 已确认 → 待财务复核 → 复核通过 → 打款中 → 已打款 → 已完结（异常：复核驳回 / 打款失败 / 结算暂停） |
| 提现单 | 待审核 → 审核通过 → 打款中 → 已到账（异常：已驳回 / 打款失败 / 待人工审核） |
| 发票 | 待开票 → 开票中 → 已开票 → 已寄出 → 已签收（异常：已作废 / 已红冲） |

## 8. 指标与埋点

**运营指标**：待确认对账单数、未结差异笔数与金额、差异平均处理时长、待复核结算单数、结算打款成功率、提现审核平均时长、自动拦截提现量、平台服务费收入、退款率、分账失败率。

**关键埋点**：对账单生成、商家确认/申诉、差异工单创建/结案、结算单复核通过/驳回、打款提交/回调、提现申请/审核/到账、发票开具/红冲、风控拦截触发。

## 9. 验收清单（EARS 汇总）

- [ ] 系统应能按「租户 × 账期 × 渠道」自动生成对账单，并支持商家确认与申诉。
- [ ] 当对账单存在未处理差异时，系统应禁止其进入结算。
- [ ] 系统应支持差异工单从发现到结案的全流程留痕与 SLA 升级。
- [ ] 当结算单进入复核环节时，系统应强制双人复核且留痕。
- [ ] 当打款失败时，系统应保留原结算单并支持原单重试。
- [ ] 当商家发起提现时，系统应校验余额、冻结、留存与结算卡一致性。
- [ ] 若租户触发风控阈值，则系统应自动限制提现并生成待办。
- [ ] 系统应保证对账单、结算单、发票、服务费台账四者金额口径一致、可相互追溯。

## 10. 与商家后台的联动

| 平台侧动作 | 商家侧表现 |
|---|---|
| 生成对账单 | `admin/recon.html` 可见对应账期账单与差异 badge |
| 差异工单处理完成 | 商家侧差异数减少，账单重算 |
| 生成结算单 | `admin/settlement.html` 出现「待确认」结算单 |
| 平台驳回结算/冻结 | 商家侧结算暂停，提示原因 |
| 提现审核结果 | `admin/withdraw.html` 状态更新并展示驳回原因 |
| 规则变更 | `admin/split-rules.html` 只读同步；`admin/payment.html` 费率展示同步 |

## 11. 待确认问题

1. **费率口径**：1%（`settlement`/`data`/`plans`）与 10%（`split-rules`）如何统一？是否保留 SaaS 订阅服务费？
2. **结算主体**：资金是否统一走平台备付金？商家自有商户号何时开放？
3. **结算发起方**：由平台自动发起还是商家申请触发？是否支持按门槛自动打款？
4. **发票方向与规则**：平台是否向商家开票？是否强制「先票后款」？
5. **打款方式**：通联代付还是银行直连？回执时效与失败处理策略？
6. **风控阈值**：退款率、提现频率、备付金水位的具体数值由谁定？
7. **双人复核范围**：哪些操作强制双人？是否区分金额档位？
8. **跨期退款冲减**：退款发生在已结算之后如何处理（追偿 / 下期冲减 / 保证金）？
9. **商家侧对账页面归属**：平台对账上线后，商家 `recon.html` 是只读结果视图还是保留操作？
