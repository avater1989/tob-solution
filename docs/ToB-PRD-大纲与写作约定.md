> 文档用途：在写终版正文前，先锁定「写什么、怎么写、以谁为准」。

## 0. 一句话定位

终版 PRD 要回答：**谁在什么约束下，用哪两端（+C 端）完成哪几条业务闭环；每一期做什么、不做什么；研发按什么验收。**

不是接口说明书，也不是原型注释合集；分册产品主文要以**功能与页面交互**讲清怎么用，工程细节进支撑层。

## 1. 真源优先级（写作铁律）

发生冲突时，按以下顺序取舍：

1. **已拍板的决策纪要**（会议结论 / 邮件 / 本仓库 `DECISIONS`）
2. **终版 PRD 正文**（本文目录下写出的条款）
3. **P0 冻结表**（模块 × 是否进本期）
4. **可点击原型**（交互与信息架构示意）
5. **战略/概念设计 PDF**（目标态与差异化，不直接当一期范围）

约定：

- 原型改**交互、文案、布局、视觉**：只更新原型与「页面索引 / 原型链接」，不自动改需求条款。
- 原型改**流程、字段、状态、权限、范围**：必须先改决策或 PRD，再改原型。
- 概念设计里的七大板块完整能力，默认进「完整方案 / 后续迭代」，除非 P0 冻结表明确纳入本期。

## 3. 终版目录（总册 A）

- 产品名称、文档版本、状态（草稿 / 评审中 / 已冻结 / 已发布）
- 负责人、评审人、最近更新日期

### 5. 端到端主路径（验收真源）

> 终版以主路径验收，不以菜单穷举验收。

5.1 路径① 内容售卖  
5.2 路径② 直播转化

## 4. 分册目录（B / C / D 共用同一写作骨架）

每个一级模块按同一模板写，禁止有的模块写故事、有的只贴截图。

### 模块文档模板（复制即用 · v0.3）

> **顺序固定**：模块目标 → 用户与场景 → 功能说明 → **页面与交互（主文）** → 业务规则摘要 → 验收 → 开放问题 → （可选）链到研发支撑。  
> 字段字典 / 完整状态机 / 接口契约：**不进产品主文正文**，放入分册附录或 `*-研发支撑.md`。

```markdown
## X.Y 模块名（例：SCRM / 直播）

### 1. 模块目标
一句话：本模块帮谁完成什么。

### 2. 用户与场景
角色职责（产品视角）+ 3～5 个典型场景故事（人怎么用）。

### 3. 功能说明（功能清单）
| 优先级 | 能力点 | 说明（产品语言） |
| P0 | … | … |
| P1 | … | 原型可有，不进本期验收 |
| 不做 | … | 明确排除 |

### 4. 信息架构与导航（若该端有侧栏/分组）
分组怎么用；P0/P1 菜单如何解读。总册仍只写一级模块，不写页面交互细节。

### 5. 页面与交互（主文核心）
每个 P0 页面一节，建议结构：
- 页面目的（一句话）
- 谁在什么时候用
- 页面结构（顶区/筛选/列表/抽屉/弹窗…）
- 主路径操作步骤（1.2.3. 点击什么 → 看到什么 → 系统反馈）
- 关键交互细节（Tab、批量、二次确认、Toast、禁用态）
- 空态 / 加载 / 失败
- 跳转关系
- 权限差异（若有）
P1 页面：短表列出名称 + 为何 P1，不写细交互。

### 6. 跨页业务流程
与总册主路径衔接的产品步骤（可配简图）；不在此展开 API。

### 7. 业务规则摘要
编号规则：R-模块-001 …（产品可读表述）；完整表可链研发支撑。

### 8. 验收标准
场景化 Given / When / Then 或检查表；对应主路径编号。

### 9. 开放问题
仅本模块未决项。

### 10. 附录索引（可选）
链到研发支撑：字段字典 / 状态迁移表 / 接口契约。
```

## 5. 写作约定（必须遵守）

### 5.1 优先级标签

| 标签 | 含义 | 能否进本期研发 Sprint |
|------|------|------------------------|
| **P0** | 本期必做，进验收 | ✅ |
| **P1** | 已想清或原型可点，不阻塞试点上线 | ❌（单独排期） |
| **P2** | 完整方案能力，仅路线图 | ❌ |
| **不做** | 明确排除或违规/灰产 | ❌，且评审中不可偷偷加回 |

原型里「能点」≠ P0。默认：**未进 P0 冻结表 = 不验收。**

### 5.2 需求表述

- 用「系统应… / 用户可以…」，避免「希望更好」「参考竞品做全」。  
- 每条业务规则可编号，便于测试引用。  
- 凡依赖外部资质、服务商、支付开通，写成 **依赖项**，不要写成已具备能力。  
- 竞品（小鹅通/螳螂/星橙）只出现在背景或附录，不作为需求句主语。

### 5.3 主路径优先于菜单

- 验收以第 5 章主路径为准。  
- 菜单上的 P1 页面可以存在于原型，但分册中必须标 P1，且不进入「发布检查清单」。

### 5.4 状态机与权限

- 有多状态对象（直播、订单、线索、退款、审核单）必须写状态机。  
- 审核类能力必须写：谁提交、谁审、驳回是否必填理由、是否可撤回。

### 5.5 字段表最低标准（放在研发支撑 / 附录）

产品主文用「页面与交互」描述筛选、批量、空态、按钮与抽屉即可。  
字段级最低标准（写入支撑层）：  
列表：筛选、列、批量操作、空态。  
表单：字段、类型、必填、默认、校验、权限。  
详情：只读块、可操作按钮、关联跳转。

### 5.5.1 深度标准 v2（校准后 · 2026-09-11 · 产品/支撑分层）

分册写到「可评审、可开发」时，**分层**如下：

| 层级 | 写什么 | 总册 | 分册产品主文 | 研发支撑 / 附录 |
|------|--------|------|--------------|-----------------|
| 页面与交互 | 每 P0 页：结构、主路径步骤、Tab/批量/确认/Toast/禁用、空载败、跳转、权限差异 | ❌ **总册仍不写页面交互细节** | ✅ **必含（主文核心）** | 可摘原型对照 |
| 业务规则 / 验收 | 编号规则摘要、场景化 Given/When/Then | 主路径验收 | ✅ 必含 | 规则全文可放支撑 |
| 字段字典 | 字段名/类型/必填/默认/校验/来源/列表展示/权限；`来源:原型` 或 `来源:产品补全` | ❌ 不写字段 | ❌ 不进主文（可一句链出） | ✅ P0 必含 |
| 状态迁移表 | 完整枚举 + From→To→触发角色→前置→副作用 | 仅原则/主路径 | 仅产品可读摘要 | ✅ P0 必含 |
| 接口契约 | Method+Path、Req/Resp、错误码、幂等/异步 | ❌ | ❌ 主文避免以 API 开篇 | ✅ P0 必含（独立支撑文档或附录） |

说明：

- **总册**只锁叙事、主路径、范围；**不写**字段与页面交互细节（见总册 4.5）。  
- **产品主文**必须让产研设测读懂「人在页面上怎么完成任务」；不要用接口清单代替交互说明。  
- **研发支撑**承接联调深度；与产品主文同模块编号，文件名建议 `ToB-PRD-0X-*-研发支撑.md`。  
- P1 能力：产品主文短表即可；字段/状态/接口一行 stub，禁止按 P0 展开。  
- 原型缺失或与冻结冲突：以冻结表与产品补全为准，标注「原型超前 / 文档超前」。  
- **样板**：`docs-out/ToB-PRD-01-商家端-SCRM.md` **v0.4-draft**（产品主文）+ `ToB-PRD-01-SCRM-研发支撑.md`；后续直播/内容/交易分册对齐同一分层。

### 5.6 与原型的同步方式

每页保留一行：

`原型：prototype/xxx.html ｜ 状态：对齐中 / 已对齐 / 原型超前 / 文档超前`

每周原型评审后，只更新这一行状态 + 变更记录，不重写整章。

### 5.7 语言与受众

- 正文中文。  
- 总册给老板看也可以读完；分册给研发测看要能估点。  
- 不把「示意 / Toast / 假数据」写成已实现后端能力；原型限制写在「实现说明」或附录。

### 5.8 变更控制

- `已冻结` 版本改 P0：走变更记录 + 知会研发估期。  
- 新增菜单/页面：先改 P0 冻结表，再改 PRD，再改原型。  
- 删除能力：在非目标表留痕，避免下个迭代又加回来吵一遍。

## 6. 「完整终版」完成定义（DoD）

同时满足才算终版 PRD 完成：

1. 总册 + 三端分册齐，目录无空章（可写「本期无 P0，见路线图」但不能省略模块裁决）。  
2. 四条（或五条）主路径均有逐步验收用例。  
3. P0 / P1 / 不做 与冻结表一致，且能指出原型中超范围页。  
4. 所有开放问题要么关闭，要么登记 Owner + 日期，且不挡 P0 开发启动。  
5. 关键状态机（线索、直播审核、订单权益）与权限矩阵已写（可在研发支撑）；产品主文含对应页面交互。  
6. 评审纪要通过：产品 / 研发 / 至少一名业务或运营。
